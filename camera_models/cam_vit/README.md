# cam_vit/

Local fine-tuning of `google/vit-base-patch16-224-in21k` for tile grades,
using the same cropped per-tile photos in `data/roboflow_dataset/` that
`cam_yolo/` trains on (built by `development/prepare_roboflow_dataset.py` —
see that script and `development/README.md`). Classifies a tile photo into
one of the grade folders currently present there: `3A`, `3B`, `4`, `5`.

This is a **local, weight-exportable counterpart** to the Roboflow-hosted
`tile-grade-classification` project (`aida-hutc5` workspace,
`tile-grade-classification-2-vit-base-patch16-224-in21k-t1`). Roboflow
trains that model on the identical base checkpoint, but its hosted ViT
training never exports weights — only a serverless inference API
(`development/evaluate_grade_model.py`). This pipeline runs the same
architecture locally, with real `.safetensors` weights you can load, export,
or eventually wire into `camera_node`.

Not an App Bricks node (like `cam_yolo/` and `development/`, this is
dev-only tooling) and not yet wired into `camera_node`'s live pipeline —
model training/evaluation only.

| File | Role |
|---|---|
| `config.yaml` | All tunable parameters — dataset paths, class list, split/oversampling, model checkpoint, training hyperparameters, augmentation. |
| `prepare_dataset.py` | Splits `data/roboflow_dataset/<grade>/*.jpg` into `train/<class>/`, `val/<class>/` — identical split logic to `cam_yolo/prepare_dataset.py` (same default seed/`val_fraction`, so both pipelines train/evaluate on the same held-out images). Rerun anytime to regenerate. |
| `dataset.py` | `TileGradeDataset` (torch `Dataset` over the split folders) + `build_transforms()` (the augmentation pipeline, see below). No I/O beyond reading image files. |
| `train.py` | Fine-tunes the configured ViT checkpoint (ImageNet-21k weights) via HuggingFace `transformers.Trainer`. Writes checkpoints to `runs/<output_dir>/`, saves the best (by val accuracy) model + processor to `runs/<output_dir>/best/`. Auto-selects GPU (CUDA, fp16) over CPU if available. |
| `val.py` | Validates a trained checkpoint's top1 accuracy + per-class precision/recall/F1 against `val/`, and writes `predictions.json`/`metrics.json`/`confusion_matrix.png` to `results/` — the same kind of artifacts `development/evaluate_grade_model.py` produces for the Roboflow models, so results are recorded the same way. |
| `predict.py` | Runs a trained checkpoint against one image or a folder, prints predicted grade + confidence. |
| `export_onnx.py` | Exports a trained checkpoint to ONNX (`runs/<output_dir>/best/model.onnx`) for deployment targets that don't run PyTorch/`transformers` directly — e.g. Edge Impulse's BYOM import for the Arduino UNO Q, see Deployment target below. |
| `dataset/` | Generated by `prepare_dataset.py` — not committed (images are repo-wide gitignored). |
| `runs/` | Training output (checkpoints, best model) per run — not committed. |
| `results/` | Written by `val.py` — `predictions.json`/`metrics.json` are committed (small, useful as a record); `confusion_matrix.png` is not (repo-wide `*.png` gitignore). |

## Usage

```bash
venv\Scripts\activate
pip install -r requirements.txt   # installs transformers + accelerate alongside cam_yolo's deps

# One-time (or whenever you want a different split/seed/oversampling): build
# the train/val split from data/roboflow_dataset/
python camera_models\cam_vit\prepare_dataset.py

# Train (reads model/epochs/augmentation from config.yaml)
python camera_models\cam_vit\train.py

# Evaluate
python camera_models\cam_vit\val.py

# Predict on a new photo
python camera_models\cam_vit\predict.py path\to\tile.jpg
```

GPU note: this repo's `.venv` already has CUDA `torch` installed (see
`cam_yolo/README.md`'s GPU install step) — `train.py` picks it up
automatically (`fp16=torch.cuda.is_available()` in `TrainingArguments`).

## Matching the Roboflow model's config, and where this diverges

The exact `tile-grade-classification` v2 dataset-version config (the
better-performing version — see `development/README.md`) was pulled from
the live Roboflow project via its `versions_get` / `trainings_describe_recipe`
API, 2026-08-25 session — not just the summary in `development/README.md`.
This pipeline's `config.yaml` augmentation block mirrors it:

| Roboflow v2 (baked into the dataset version) | `camera_models/cam_vit/config.yaml` | Match |
|---|---|---|
| `brightness`: ±10% (brighten + darken) | `brightness_percent: 10` | Close — approximated with `torchvision.ColorJitter(brightness=0.10)` rather than Roboflow's exact implementation, but same underlying linear-scaling operation. |
| `exposure`: ±5% | `exposure_percent: 5` | Approximated as a **second, independent** `ColorJitter` brightness pass, since Roboflow exposes brightness/exposure as two separate sliders on what is visually the same kind of operation — kept as two knobs here for the same reason. |
| `ninety`: clockwise / counter-clockwise / upside-down | `ninety_rotation: true` | Exact — `RandomNinetyRotation` in `dataset.py` picks uniformly from {0°, 90°, 180°, 270°}, **not** continuous-angle rotation (unlike `cam_yolo`'s `degrees: 180.0`, which is a full-range random rotation — a real, deliberate difference between the two pipelines, see below). |
| `flip`: horizontal + vertical | `hflip_prob: 0.5`, `vflip_prob: 0.5` | Exact. |
| *(no contrast step)* | *(no contrast step)* | Exact — deliberately omitted. Roboflow's v3 added `contrast: Adaptive Equalization` on top of this same augmentation and accuracy **dropped** from 84.2% to 63.2% held-out, concentrated in grade-5 recall (`development/README.md`). Don't add CLAHE/histogram-equalization preprocessing here without re-testing against a held-out set first. |
| `resize`: 640×640, `auto-orient` | `image_size: 224` | **Deliberately different, not a bug.** Roboflow's 640×640 resize is baked into the dataset version as shared machinery (the same resize step object-detection projects use), but `vit-base-patch16-224-in21k` architecturally trains at 224×224 — Roboflow downsamples again internally at train time. This pipeline resizes straight to 224 (the checkpoint's native resolution) since there's no shared-pipeline constraint to preserve locally. |
| 3× per-image dataset multiplier (`image.versions: 3`), applied uniformly across classes | class-balancing oversampling (`split.oversample_train: true`, mirrors `cam_yolo`) | **Deliberately different.** Roboflow's multiplier does not rebalance class ratios (each class gets ~3× regardless of its size), so the source imbalance (3A=140, 3B=109, 4=74, 5=53) persists through it. This pipeline instead reuses `cam_yolo`'s approach: oversample minority-class train images up to the majority class's count *before* the (identical) online augmentation is applied — a version-2-style config plus explicit class balancing, since class imbalance was never something Roboflow's own config addressed. |

Model architecture itself is an exact match: `google/vit-base-patch16-224-in21k`
is the HuggingFace ID for the same base checkpoint Roboflow's
`vit-base-patch16-224-in21k` model type fine-tunes from (confirmed via
`trainings_describe_recipe`) — ViT-Base, patch size 16, 224px, pretrained on
ImageNet-21k. Roboflow's ViT offering has no small/large size option, so
there's nothing to choose between here.

## Comparing against the other two grade classifiers

Three models now exist for the same 4-class problem, trained/evaluated on
different (but overlapping) data:

| Model | Where | Held-out accuracy | Exportable weights? |
|---|---|---|---|
| `tile-grade-classification` v2 (Roboflow, ViT-Base) | Roboflow hosted | 84.2% (16/19, Roboflow's own 19-image held-out test split) | No — hosted inference API only |
| `cam_yolo` (`yolo26s-cls`, local) | `camera_models/cam_yolo/runs/tile_grade_cls-aug-s-gpu` | 85.5% top1 (on its own 76-image val split) | Yes |
| `cam_vit`, trained on the **original** dataset (2026-08-25) | `camera_models/cam_vit/runs/tile_grade_vit/best` (superseded, see below) | **93.4% top1** (71/76, clean 76-image val split) | Yes |
| `cam_vit`, trained on the **augmented** dataset (2026-08-26, current) | `camera_models/cam_vit/runs/tile_grade_vit/best` | **92.1% top1** (70/76, same clean 76-image val split — apples-to-apples) | Yes |

`cam_vit`'s per-class breakdown, original-dataset run, on the clean 76-image
val split (2026-08-25 training run, early-stopped at epoch 23/30, best
checkpoint from epoch 15):

| class | precision | recall | f1 | support |
|---|---|---|---|---|
| 3A | 1.000 | 1.000 | 1.000 | 28 |
| 3B | 0.917 | 1.000 | 0.957 | 22 |
| 4 | 0.812 | 0.867 | 0.839 | 15 |
| 5 | 1.000 | 0.727 | 0.842 | 11 |

3A and 3B were classified perfectly (28/28, 22/22). All 5 errors were
adjacent-grade confusions — 2 of 15 grade-4 tiles predicted as 3B, 3 of 11
grade-5 tiles predicted as 4 — the same off-by-one error shape `cam_yolo`
and Roboflow's own model show on this dataset, never a confusion between
non-adjacent grades (e.g. 3A vs. 5). Training took ~3.4 minutes (23 epochs)
on this dev machine's RTX 1000 Ada.

## Retrain experiment: does `development/augment_dataset.py`'s offline augmentation help? (2026-08-26)

**Short answer: no, not measurably.** Retrained the identical pipeline
(same config, same architecture, same online augmentation) on
`data/roboflow_dataset_augmented` (376 → 1000 images via mild affine
rotation/shear + perspective, see `development/README.md`) instead of the
original `data/roboflow_dataset`, then evaluated the resulting checkpoint
two ways:

| Eval set | Accuracy | Notes |
|---|---|---|
| Augmented dataset's own val split (202 images) | 88.1% (178/202) | **Not comparable to the 93.4%/92.1% numbers above** — this val split itself now contains mildly rotated/sheared/perspective-distorted images (grouped by source photo to avoid leakage, see `prepare_dataset.py`'s docstring, but still a harder/different benchmark than clean photos). A lower number here does not mean a worse model. |
| Same clean, non-augmented 76-image val split used by every other run in this table | **92.1% (70/76)** | The fair, apples-to-apples comparison against the original-dataset run's 93.4% (71/76). |

70/76 vs. 71/76 is a one-image difference on a 76-image set — statistically
indistinguishable, not a real improvement or regression. The confusion
matrix (`results_vs_clean_baseline/confusion_matrix.png`) shows the same
off-by-one error pattern as before (grade 4↔3B, grade 5↔4), just
redistributed by one image. **Conclusion: this offline augmentation didn't
help `cam_vit` on this dataset.** Plausible reasons, roughly in order of
suspicion:

- `cam_vit` already applies its own online rotation (full 90°-step, i.e.
  `RandomNinetyRotation`) and flip augmentation every epoch (see the config
  table above) — the *marginal* new information from adding mild
  affine/perspective on top may be small when a strong rotation/flip
  invariance is already being trained in.
- The dataset is still small in an absolute sense (376 real source photos;
  1000 after augmentation is still mostly near-duplicates of those same 376
  underlying tiles, not 1000 independent samples) — augmentation multiplies
  *variety of presentation*, not real information content, and can't
  substitute for more actual distinct tiles.
- ViT-Base (86M params) fine-tuned with a strong ImageNet-21k prior may
  already be well past the point where this dataset's limited real
  diversity is the bottleneck, not insufficient geometric augmentation.

`camera_models/cam_vit/config.yaml`'s `source_dataset_dir` is left pointing
at the augmented set (current default) since it's not measurably worse
either — but don't expect it to outperform the original dataset without
more real (not just re-transformed) tile photos. `results/` reflects the
current (augmented-trained) checkpoint's own native val split (202 images,
88.1%); `results_vs_clean_baseline/` holds the fair 76-image comparison
above.

`cam_vit` and `cam_yolo` share the same seed=42/`val_fraction=0.2`/oversampling
split logic. `cam_yolo` still trains on the original `data/roboflow_dataset`
(76-image val split), while `cam_vit` (as of 2026-08-26) trains on the
offline-augmented copy (202-image val split, itself containing augmented
images — see the retrain experiment above) — so their `val.py` numbers
aren't directly comparable anymore without going through the same clean
76-image baseline used in the retrain-experiment table. Neither is directly
comparable to Roboflow's 84.2%, which uses Roboflow's own held-out 19-image
split (image IDs hardcoded in `development/evaluate_grade_model.py`'s
`TEST_SET`) — different images, different split.

## Deployment target: Arduino UNO Q real-time inference (2026-08-26)

The eventual `camera_node` target is a physical Arduino UNO Q (Qualcomm
QRB2210: quad-core Kryo CPU up to 2GHz, Adreno 702 GPU, dual ISP, an
always-on Hexagon DSP that Qualcomm's own product brief describes as
targeting low-power sensor fusion/audio — not a dedicated vision NPU. 2-4GB
LPDDR4 RAM, Debian Linux). Arduino added full Edge Impulse integration to
App Lab for the UNO Q in March 2026, including **Bring Your Own Model
(BYOM)** — importing a `.onnx`/`.tflite`/SavedModel directly with on-device
latency/memory profiling, rather than only training from scratch in Edge
Impulse Studio.

`export_onnx.py` exists for this, but **ViT-Base is the risky candidate
here**: its exported ONNX is **328MB**, ~16x `cam_yolo`'s `yolo26s-cls`
export (21MB) — for real-time inference on hardware with no dedicated
vision NPU, `camera_models/cam_yolo/README.md`'s smaller classification
heads are the safer bet. Sanity-checked this export against the original
HuggingFace model on a 20-image spot check (18/20 correct, consistent with
the augmented-trained model's own ~88-92% range) — the export itself is
faithful, this is a size/latency concern, not a correctness one.

**Not yet profiled on real hardware** — same blockers as `cam_yolo`: the lab
UNO Q wasn't reachable over its hotspot this session, and BYOM requires an
Edge Impulse account/API key that doesn't exist yet in `.env`. If the board
profiling shows ViT-Base is too slow, `cam_yolo`'s `yolo26n-cls` (1.5M
params, the smallest trained variant) is the fallback to try next before
considering a dedicated MobileNet/EfficientNet-Lite architecture.

## Known limitations

- Same small-dataset caveat as `cam_yolo`: ~376 source images across 4
  classes (448 train after oversampling, 76 val) is small for an 86M-param
  model (ViT-Base) — much larger than `yolo26s-cls`'s 5.4M params, so expect
  faster overfitting and higher run-to-run variance; watch val accuracy
  during training, not just train loss. `train.py`'s early stopping
  (`train.patience`) is there specifically for this, and did trigger on the
  2026-08-25 run (stopped at epoch 23, kept the epoch-15 checkpoint).
- Same grade-label caveat as `cam_yolo`: `3A`/`3B`/`4`/`5` come from how the
  source photos were organized during capture, not a validated
  ground-truth grading pass — see `development/prepare_roboflow_dataset.py`'s
  docstring. This trains a grade classifier, not a defect detector.
- The brightness/exposure approximation (two independent `ColorJitter`
  passes rather than Roboflow's exact pixel-level implementation) and the
  discrete-rotation vs. `cam_yolo`'s continuous-rotation difference mean
  "same type of processing" is a close match, not a bit-for-bit
  reproduction — see the config table above for exactly where and why.
- **`transformers` must stay pinned below v5** (`requirements.txt` pins
  `transformers==4.46.3`, `huggingface_hub==0.36.2`, `tokenizers==0.20.3`) —
  confirmed during this session that `transformers==5.15.1` silently fails
  to load `google/vit-base-patch16-224-in21k`'s pretrained backbone weights:
  v5 renamed ViT's internal layer/attention parameter names (fused
  `q_proj`/`k_proj`/`v_proj`/`o_proj` vs. the checkpoint's classic
  `attention.attention.query`/`key`/`value`), so every encoder-layer weight
  loads as MISSING/UNEXPECTED and the model would silently train from a
  randomly-initialized backbone instead of the pretrained one — no error is
  raised, only a load-report warning easy to miss. Verify with
  `python -c "from transformers import ViTForImageClassification; ViTForImageClassification.from_pretrained('google/vit-base-patch16-224-in21k', num_labels=4)"`
  after any future `transformers` upgrade — it should report only
  `classifier.weight`/`classifier.bias` as newly initialized, nothing else.
- **Downloading the checkpoint from HuggingFace was unreliable on this dev
  machine's connection** (2026-08-25 session) — `transformers`' own
  downloader failed twice (once via a CDN error on the `hf_xet`
  fast-download path, once via a read timeout on the plain-HTTP fallback)
  before the ~346MB `model.safetensors` completed via a manual
  `curl -C - --retry` (resume + retry + stall-detection) into HuggingFace's
  local hub cache. If a fresh machine hits the same flakiness: set
  `HF_HUB_DISABLE_XET=1` to skip the flakier fast-download path first; if
  plain HTTP downloads also time out, download `model.safetensors` directly
  with `curl -C -` (resumable) and place it at
  `~/.cache/huggingface/hub/models--google--vit-base-patch16-224-in21k/blobs/<sha256-from-the-.incomplete-filename>`
  plus a copy at `.../snapshots/<commit>/model.safetensors` — `from_pretrained`
  then loads it offline with no further network needed. Once cached,
  `train.py`/`val.py`/`predict.py` were run with `HF_HUB_OFFLINE=1` to avoid
  any further network calls on this connection; that's optional once the
  cache is warm and network is reliable.
