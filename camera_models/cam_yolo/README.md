# cam_yolo/

YOLO26 image-classification training for tile grades, using the cropped
per-tile photos in `data/roboflow_dataset/` (built by
`development/prepare_roboflow_dataset.py` from the raw `data/` captures —
see that script and `development/README.md`). Classifies a tile photo into
one of the grade folders currently present there: `3A`, `3B`, `4`, `5`.

Not an App Bricks node (like `development/`, this is dev-only tooling, not
one of `acoustic_node/`/`camera_node/`/`pick_place_node/`) and not yet
wired into `camera_node`'s live pipeline — this is model training/
evaluation only. Whether/how the resulting weights get deployed into
`camera_node` is a separate, later decision.

| File | Role |
|---|---|
| `config.yaml` | All tunable parameters — source/output dataset paths, class list, train/val split fraction + seed + oversampling, training hyperparameters (model, epochs, augmentation, regularization). |
| `prepare_dataset.py` | Splits `data/roboflow_dataset/<grade>/*.jpg` into the `train/<class>/`, `val/<class>/` layout Ultralytics classification training expects ([docs](https://docs.ultralytics.com/datasets/classify/)). Copies files (source images untouched); optionally oversamples minority-class train images to match the largest class (`split.oversample_train`, see Experiments below). Rerun anytime to regenerate the split. |
| `train.py` | Fine-tunes the configured pretrained checkpoint (ImageNet weights) on the split dataset — model/epochs/augmentation all come from `config.yaml`. Writes checkpoints/metrics to `runs/<name>/`. Auto-selects GPU (CUDA) over CPU if available. |
| `val.py` | Validates a trained checkpoint's top1/top5 accuracy against `val/`. |
| `predict.py` | Runs a trained checkpoint against one image or a folder, prints predicted grade + confidence. |
| `export_onnx.py` | Exports a trained checkpoint to ONNX (`runs/<name>/weights/best.onnx`) for deployment targets that don't run PyTorch/Ultralytics directly — e.g. Edge Impulse's BYOM import for the Arduino UNO Q, see Deployment target below. |
| `dataset/` | Generated by `prepare_dataset.py` — not committed (images are repo-wide gitignored). |
| `runs/` | Ultralytics training output (weights, metrics, plots) per run name — not committed. |

## Usage

```bash
venv\Scripts\activate
pip install -r requirements.txt   # installs ultralytics + CPU-only torch by default

# For GPU training (much faster — see Experiments below), reinstall torch
# with CUDA support after the above (Windows, NVIDIA GPU with a recent
# driver — check with `nvidia-smi`). requirements.txt can't express this
# itself since it needs a non-default package index:
pip install torch==2.6.0+cu124 torchvision==0.21.0+cu124 --index-url https://download.pytorch.org/whl/cu124

# One-time (or whenever you want a different split/seed/oversampling): build
# the train/val split from data/roboflow_dataset/
python camera_models\cam_yolo\prepare_dataset.py

# Train (reads model/epochs/augmentation from config.yaml)
python camera_models\cam_yolo\train.py

# Evaluate
python camera_models\cam_yolo\val.py

# Predict on a new photo
python camera_models\cam_yolo\predict.py path\to\tile.jpg
```

## Experiments (2026-08-21)

Four configurations were compared to improve on an initial baseline, per-class
validation recall (76 val images: 3A=28, 3B=22, 4=15, 5=11):

| Run (`runs/<name>`) | Model | Device | top1 | 3A | 3B | 4 | 5 |
|---|---|---|---|---|---|---|---|
| `tile_grade_cls-2` (baseline) | yolo26n-cls | CPU | 0.803 | 0.86 | 0.77 | 0.80 | 0.73 |
| `tile_grade_cls-aug-n` | yolo26n-cls | CPU | 0.829 | 0.79 | 0.95 | 0.67 | 0.91 |
| `tile_grade_cls-aug-n-gpu` | yolo26n-cls | GPU | 0.776 | 0.82 | 0.86 | 0.60 | 0.73 |
| **`tile_grade_cls-aug-s-gpu`** (current default) | **yolo26s-cls** | **GPU** | **0.855** | 0.79 | **0.91** | **0.80** | **1.00** |

The baseline used `yolo26n-cls` with no augmentation beyond Ultralytics'
classification defaults and no class balancing. Two changes were layered on
top for the `-aug-*` runs:

1. **Class balancing** (`split.oversample_train: true` in `config.yaml`) —
   the source data is imbalanced (3A=140, 3B=109, 4=74, 5=53 images), which
   biases a classifier toward the majority classes. `prepare_dataset.py`
   duplicates minority-class train images up to the majority class's count
   (112 each after the val split). Ultralytics re-applies its random
   augmentation independently each time a duplicated path is sampled, so
   this is not a literal no-op — it's a standard, cheap fix for imbalance
   given the framework has no built-in weighted sampler for classification.
2. **Rotation/flip augmentation + head dropout** (`train.degrees: 180`,
   `train.flipud: 0.5`, `train.dropout: 0.2`, `train.cos_lr: true`) — a
   tile photo has no canonical "up" (tiles get placed/photographed in any
   orientation), so full rotation invariance reflects something real about
   the domain rather than an artificial augmentation. Dropout regularizes
   the classification head given how small the dataset is.

With the small `yolo26n-cls` backbone, these changes fixed class 3B's recall
(0.77→0.95 on CPU) but **cost class 4** accuracy (0.80→0.67) — the model
didn't have enough capacity to fit the harder, more-augmented, class-balanced
data without trading one class off against another; GPU vs. CPU runs of the
identical config also showed real run-to-run variance (0.829 vs. 0.776) given
how small this dataset is (300-448 train images). Moving to the larger
`yolo26s-cls` backbone (5.4M params vs. 1.5M) resolved that trade-off:
enough capacity to benefit from both fixes at once, improving every class
except a small, roughly noise-level dip on 3A. `config.yaml` now points at
this run (`tile_grade_cls-aug-s-gpu`) as the default for `val.py`/`predict.py`.

### GPU training

This dev machine has an NVIDIA RTX 1000 Ada (6GB VRAM) that CPU-only `torch`
(the `requirements.txt` default) doesn't use. With CUDA `torch` installed
(see Usage above), Ultralytics auto-selects the GPU with no config change —
observed speedup was roughly **15-20x** (e.g. 100 CPU epochs on
`yolo26n-cls` took ~12 minutes; 94 GPU epochs on the larger `yolo26s-cls`
took ~3 minutes). This is what made the 4-way experiment comparison above
practical to run at all — always install CUDA `torch` before iterating on
this dataset if a compatible GPU is available (`nvidia-smi` to check).

### Further improvement ideas, roughly in order of expected impact

- **More real data is the single biggest lever.** 376 images across 4
  classes is a small dataset for a 4-way classifier; every experiment above
  is fighting sample-size noise as much as anything else (note the
  CPU-vs-GPU variance on the identical `aug-n` config). This is also the
  answer to "can we do reinforcement learning to improve this" — RL fits
  problems with sequential actions and a reward signal (e.g. a robot
  learning to grip), not a static image classification task; what actually
  helps here is standard supervised-learning leverage: more labeled data,
  data augmentation (done above), transfer learning (already used — these
  are ImageNet-pretrained checkpoints, not trained from scratch), and
  regularization for small datasets (dropout, done above).
- **Active learning loop, via the Roboflow project this dataset already
  lives in**: deploy a trained checkpoint, run it against new real tile
  photos as they're captured, and route low-confidence/misclassified
  predictions back into the training set for review — Roboflow's Active
  Learning / annotation-job tooling supports exactly this loop and is
  already connected to this workspace. This is the practical analogue of
  "reinforcement" here: an iterative feedback loop, just supervised rather
  than reward-based.
- **k-fold cross-validation** instead of a single fixed 80/20 split, given
  how small `val/` is (76 images, some classes with only 11-15) — the
  per-class recall numbers above have real sampling noise; a fixed split
  makes single runs somewhat unreliable for deciding "did this really get
  better."
- **Ensembling** the `aug-n`/`aug-s` checkpoints (average softmax
  probabilities) could recover some of what each individual model misses,
  at the cost of 2x inference time — likely not worth it for a 3.2-11MB
  model given more data or more epochs on the winning config are cheaper
  wins.
- Hyperparameter sweep beyond what was tried here (learning rate, batch
  size, `mixup`/`cutmix`, `imgsz`) — not attempted because the class-level
  wins above already came from more structural changes (backbone size,
  class balance, augmentation), which is where the effort was spent first.

## Deployment target: Arduino UNO Q real-time inference (2026-08-26)

The eventual `camera_node` target is a physical Arduino UNO Q (Qualcomm
QRB2210: quad-core Kryo CPU up to 2GHz, Adreno 702 GPU, dual ISP, an
always-on Hexagon DSP that Qualcomm's own product brief describes as
targeting low-power sensor fusion/audio — not a dedicated vision NPU. 2-4GB
LPDDR4 RAM, Debian Linux). Arduino added full Edge Impulse integration to
App Lab for the UNO Q in March 2026 (confirmed via Arduino's own blog and
Edge Impulse's docs), including **Bring Your Own Model (BYOM)** — importing
a `.onnx`/`.tflite`/SavedModel directly rather than only training from
scratch in Edge Impulse Studio, with on-device latency/memory profiling
before you commit to deploying it.

`export_onnx.py` exists for exactly this: `yolo26s-cls`'s exported ONNX is
**21MB** (vs. `cam_vit`'s 328MB for ViT-Base — see `camera_models/cam_vit/README.md`),
making this pipeline's small classification heads (`yolo26s-cls`, 5.4M
params, or `yolo26n-cls`, 1.5M params — both trained in the Experiments
table above) the much safer real-time/edge candidate on hardware with no
dedicated vision NPU. Sanity-checked the ONNX export against the original
PyTorch model on a 20-image spot check (15/20 correct, consistent with the
full val set's 85.5%) — the export is faithful, not broken.

**Not yet done**: actually profiling on the real board. The lab UNO Q
(`tools/uno_q/`) wasn't reachable over its hotspot during this session, and
BYOM/on-device profiling requires an Edge Impulse account (no
`EDGE_IMPULSE_API_KEY` exists yet, unlike `ROBOFLOW_API_KEY` in `.env`).
This ONNX export is the ready-to-upload artifact for whenever both of those
are available.

## Known limitations

- Small dataset (~376 images across 4 classes as of 2026-08-20, see
  `data/roboflow_dataset/` counts) — expect this classifier to overfit
  easily; watch the `val/` accuracy in `runs/tile_grade_cls/`, not just
  train loss.
- The `3A`/`3B`/`4`/`5` grade labels come from how the source photos were
  organized during capture, not a validated ground-truth grading pass —
  see `development/prepare_roboflow_dataset.py`'s docstring (repo owner,
  2026-08-16 session): lower grades are known to contain real damaged
  tiles, but no defect-level (crack vs. corner) annotation exists yet.
  This trains a single grade classifier, not a defect detector.
- `imgsz: 224` with default `CenterCrop`/`RandomResizedCrop` transforms
  (Ultralytics classify default) assumes a roughly square input — the
  cropped tile photos from `prepare_roboflow_dataset.py` should already be
  close to square, but this hasn't been specifically verified per class.
